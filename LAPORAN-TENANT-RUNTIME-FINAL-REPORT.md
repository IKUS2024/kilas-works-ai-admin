# KILAS WORKS BUSINESS HUB V2 — TENANT RUNTIME FINAL REPORT

Tenant-specific WhatsApp sender: DONE. `app.py`'s `_get_tenant_whatsapp_channel_safe(tenant_id)` reads the resolved tenant's own `phone_number_id` + `credentials_reference` (via `client-hub/tenant_config_service.get_tenant_whatsapp_channel`), resolves the actual access token from THIS process's own environment, and activates it per-request via a thread-local (`_set_active_whatsapp_channel` / `_active_whatsapp_phone_number_id()` / `_active_whatsapp_access_token()`), reset unconditionally at the top of every webhook call. Every outgoing call (`send_whatsapp_message`, `send_whatsapp_image`, `send_typing_indicator`, `upload_media`, `upload_media_bytes`, `download_whatsapp_media`, `send_qr_code`, `send_catalog_pdf`) now reads the active channel instead of the hardcoded global `WHATSAPP_PHONE_NUMBER_ID`/`WHATSAPP_ACCESS_TOKEN`.

No Kilas sender fallback for client: DONE. If a resolved client tenant has no complete channel (`_get_tenant_whatsapp_channel_safe` returns `None` — tenant not ACTIVE, no `tenant_whatsapp_config` row, or the `credentials_reference` env var isn't actually set on this process), the webhook logs it and returns `200` without sending anything. There is no code path where a client tenant's reply is sent through Kilas Works' own global channel.

Tenant-scoped history: DONE. `_ck(tenant_id, number)` produces a compound key (`f"T{tenant_id}:{number}"` for a real tenant, the bare number for Kilas Works' own traffic) used for every read/write of `conversations`, `customer_names`, `customer_language`, and the DB-backed message log (`save_message_to_db`/`load_recent_messages_from_db`) inside `call_claude`. The same customer phone number messaging two different tenants (or a tenant and Kilas Works itself) never shares history, facts, or captured name.

Tenant-scoped appointment state: PARTIAL / DEFERRED BY DESIGN. There is no per-tenant business-hours/availability config yet, so rather than half-build a tenant-aware appointment engine against Kilas Works' own `DEFAULT_MEETING_SLOT_TIMES`/`appointments`/`meeting_requests` store, the appointment/booking engine is kept entirely Kilas-Works-own: a resolved client tenant's customer trying to book gets a graceful "hubungi tim kami langsung" decline instead of ever touching Kilas Works' own slots/hours. This is a known limitation, not a leak — see trace 2 below.

Tenant-scoped human takeover: ALREADY CORRECT (confirmed unchanged this cycle). `wa_takeover_service.get_state(tenant_id, customer_phone)` / `tenant_config_service.get_conversation_mode` key strictly by `(tenant_id, customer_phone)`; regression-tested in `test_multi_tenant_runtime_safety.py::test_takeover_scoped_per_tenant_and_per_customer_still_holds`.

Basic runtime gating: DONE. `image_understanding` and `owner_commands` are now actually checked against `FEATURE_MATRIX` at runtime for a resolved tenant (previously unchecked — any tenant's "owner" could reach the full owner-command bridge, and any tenant's customer image went straight to Claude vision). `voice_note` was already gated and is re-verified. Basic has `appointment=False` and `voice_note=False`, `owner_commands=False`, `image_understanding=False` in `client-hub/feature_flags.py`'s `FEATURE_MATRIX`.

Pro runtime gating: DONE. Pro has every flag `True` in `FEATURE_MATRIX`; voice note, image understanding, and owner commands all run for a Pro tenant exactly as for Kilas Works' own number (appointment booking itself is the one exception — see "Tenant-scoped appointment state" above, which applies uniformly regardless of package since no tenant has a booking backend yet).

Upgrade entitlement: CONFIRMED (regression-tested, not newly built). `_get_tenant_features_safe` re-reads `tenant_config_service.get_tenant_features(tenant_id)` on every message — no caching — so a package change takes effect on the very next customer message (`test_upgraded_tenant_sees_new_features_on_very_next_message`).

Platform owner vs tenant owner: DONE. `is_kilas_platform_tenant(tenant_id)` (`tenant_id is None`) is the single stable signal used everywhere. `_get_tenant_owner_notify_target_safe` routes `notify_owner`/`notify_owner_new_message`/`notify_owner_question` to Kilas Works' own `OWNER_WHATSAPP_NUMBER` only for `tenant_id is None`, and to that tenant's own `trusted_owner_phone` otherwise — never falling back from one to the other. `active_customer_context` (Kilas's own "terusin ke customer" default) is now only updated for Kilas Works' own conversations; a separate `_tenant_active_customer_context` dict, keyed `(tenant_id, owner_phone)`, is used for tenant owners. Known limitation: `notify_owner_question`'s free-form-discussion-then-relay flow (`pending_owner_questions`) is still Kilas-Works-own-owner-only — a tenant owner is notified but the auto-relay-back-to-customer conversational shortcut isn't tenant-aware yet.

Tenant appointment config: NOT YET BUILT (documented limitation, not silently ignored). No per-tenant office-hours/slot-availability table exists. The appointment engine is deliberately disabled end-to-end for every resolved client tenant (Basic and Pro alike) rather than leaking Kilas Works' own hours/slots into a tenant's conversation.

Tenant payment config: NOT YET BUILT (documented limitation). No per-tenant bank-account/payment-details field exists. `[GIVE_PAYMENT_INFO]` is now branch-gated: for Kilas Works' own conversation it fills in `PAYMENT_CONFIG` (Kilas's own BCA account) exactly as before; for a resolved client tenant it is replaced with a generic "confirm directly with our team" line — Kilas Works' own bank account can never appear in a client tenant's conversation.

WhatsApp real connection validation: DONE (uniqueness fully live-tested in this sandbox; the Meta Graph API leg is implemented but only exercised via its fail-safe / stubbed-success paths — see Known limitations). `client-hub/routes_admin.py`'s `connect_whatsapp` route now calls `provisioning.validate_and_connect_whatsapp(business_id, admin, phone_number_id, waba_id, credentials_reference)`, which (1) checks `repo.find_business_id_by_phone_number_id()` for a different tenant already owning this Phone Number ID, and (2) attempts a live `GET https://graph.facebook.com/v21.0/{phone_number_id}` using the token the `credentials_reference` pointer names, resolved from this process's own environment, with an 8s timeout. `businesses.whatsapp_connected` (the V1 activation gate `provisioning.activate_tenant()` already checks) is now ONLY ever set `True` by the route on an actual `CONNECTED` verdict — never on a bare form submission. Any failure (duplicate ID, missing/invalid credential, network/DNS/timeout error, non-2xx response) leaves `tenant_whatsapp_config.connection_status = 'VALIDATION_FAILED'` and the tenant not connected/not activatable. The real access-token value is never included in the flash message, a log line, or the audit `detail` string (verified by `test_whatsapp_validation_never_logs_or_returns_the_real_access_token_value`).

Duplicate Phone Number ID protection: DONE. `repo.find_business_id_by_phone_number_id(phone_number_id, exclude_business_id)` checks both `tenant_whatsapp_config.phone_number_id` and the legacy `businesses.whatsapp_phone_number_id` column for any OTHER business already holding this ID; `validate_and_connect_whatsapp` refuses (status `VALIDATION_FAILED`, reason `duplicate_phone_number_id: ...`) before any live network call is even attempted. Regression-tested end to end.

Database source of truth: VERIFIED BY READING THE ACTUAL CODE. `app.py`'s Client Hub bridge (near the top of the file) does `sys.path.insert(0, ".../client-hub")` and then plain Python `import tenant_config_service as _tcs`, `import wa_takeover_service as _wa_takeover`, `import wa_project_bridge as _wa_bridge` — these are IN-PROCESS module imports, not an HTTP/API call to a separately-running Client Hub server. Transitively, those modules import `client-hub/repo.py` and `client-hub/db.py`. `client-hub/db.py` reads its own `DATABASE_URL` env var at module import time (`DATABASE_URL = (os.environ.get("DATABASE_URL") or "").strip()`) and falls back to a local SQLite file (`CLIENT_HUB_DB_PATH`) if unset. Separately, `app.py` itself (line ~748) reads `DATABASE_URL = os.environ.get("DATABASE_URL", "")` for its OWN chat-history/leads Postgres connection (`get_db_connection()`), which is a DIFFERENT connection object than client-hub/db.py's connection-per-thread. Within a single process both reads are the same OS environment variable, so they can never literally disagree there. The real risk is at the DEPLOYMENT level: `LAPORAN-CLIENT-HUB-PRODUCTION-FOUNDATION.md` (section 12) documents that Client Hub is meant to ALSO be deployed as its own SEPARATE Render web service (its own admin UI, its own env panel) for staff onboarding/approval/connect-WhatsApp/activate — a genuinely different process from the bot's own Render service. For the `ENABLE_MULTI_TENANT` bridge inside the bot's own service to see the SAME tenant data that separately-deployed admin service manages, **both Render services' `DATABASE_URL` must be set, independently, to the identical production Postgres connection string** — nothing enforces that automatically. Added: a startup log warning in `app.py`'s bridge-init block that fires when `ENABLE_MULTI_TENANT=true` but `DATABASE_URL` is unset on the bot's own service (the single most likely real misconfiguration — client-hub/db.py would otherwise silently fall back to a local SQLite file no admin ever writes to, and every tenant lookup would fail closed as "no tenant" rather than erroring loudly).

## Manual traces (Task E)

**1. Kilas Works direct customer asks "Growth berapa?"**
Webhook POST hits `receive_webhook()` in `app.py`. `_incoming_phone_number_id = value["metadata"]["phone_number_id"]` is Kilas Works' own number, which has never been registered as a Client Hub tenant, so `_resolve_tenant_id(_incoming_phone_number_id)` → `tenant_config_service.get_tenant_by_phone_number_id()` finds no ACTIVE business and returns `tenant_id = None`. `is_kilas_platform_tenant(None)` is `True`. No feature-gate check runs (feature gating is only applied when `tenant_id is not None`). The message is plain text, so `user_text = message["text"]["body"]`. `call_claude(from_number, user_text, tenant_id=None, tenant_context_block="")` is invoked; inside it, `build_customer_system_prompt(scoped_number, tenant_context_block="")` builds the prompt using Kilas Works' own `SYSTEM_PROMPT`/`PRICING_CONFIG`-derived catalog text, plus `_build_live_price_sync_note_safe()` (since `tenant_context_block` is empty) which calls `get_live_catalog_price_safe("growth", ...)`-style lookups against Client Hub's own `catalog_service.list_active_catalog()` to see if the "Growth" package price has diverged from the hardcoded figure baked into `SYSTEM_PROMPT`; if it has, an extra note is appended so Claude answers with the live number. Claude (Haiku first, escalating to Sonnet if needed) generates the reply. Outgoing send: `_active_whatsapp_phone_number_id()`/`_active_whatsapp_access_token()` return the GLOBAL `WHATSAPP_PHONE_NUMBER_ID`/`WHATSAPP_ACCESS_TOKEN` (the thread-local channel override is never set, since `is_kilas_platform_tenant` is `True`), and `send_reply_bubbles()` → `send_whatsapp_message()` sends from Kilas Works' own number.

**2. Basic-tier coffee shop customer asks "Bisa booking jam 3?"**
`_incoming_phone_number_id` matches that coffee shop's registered `phone_number_id`; `_resolve_tenant_id()` → `tenant_config_service.get_tenant_by_phone_number_id()` returns the coffee shop's real `business_id` as `tenant_id`. `is_kilas_platform_tenant(tenant_id)` is `False`. The webhook activates the tenant's own outgoing channel via `_get_tenant_whatsapp_channel_safe(tenant_id)` → `tenant_config_service.get_tenant_whatsapp_channel(tenant_id)` and `_set_active_whatsapp_channel(...)`; if that tenant's channel isn't fully configured the request is dropped (200, no send) rather than falling back to Kilas Works. Message type is text; the appointment-related regex matches (`meeting_pref_match`, `book_match`, etc.) still fire on the phrase, but because `is_kilas_tenant` is `False`, the appointment-engine branch takes the `not is_kilas_tenant` path and NEVER checks `FEATURE_MATRIX["AI_ADMIN_BASIC"]["appointment"]` (which is `False`) — appointment handling is disabled uniformly for every client tenant regardless of package, appending "Untuk jadwal ketemu/booking, mohon hubungi langsung tim kami ya, Kak." to the reply instead of running Kilas Works' own `build_appointment_context()`/slot-booking logic. Knowledge source: `_build_tenant_context_block_safe(tenant_id)` (this coffee shop's own onboarding data/FAQ/services from `tenant_config_service.get_tenant_config`), passed into `call_claude(..., tenant_context_block=...)`; `build_customer_system_prompt` uses `appointment_context = ""` (never Kilas's own hours) whenever `is_tenant_context` is true. Conversation-state scope: `_ck(tenant_id, from_number)` = `f"T{tenant_id}:{from_number}"`, isolating this conversation from both Kilas Works' own history and any other tenant's. Outgoing send: the coffee shop's own `phone_number_id`/access token (set via `_set_active_whatsapp_channel` above), never Kilas Works' global channel.

**3. Pro-tier tenant customer sends a voice note**
Tenant resolution identical to trace 2 (`_resolve_tenant_id` off this tenant's own `phone_number_id`), `tenant_id` = that Pro tenant's `business_id`. `msg_type == "audio"` branch: `_tenant_voice_ok = _get_tenant_features_safe(tenant_id).get("voice_note", False)` reads `tenant_config_service.get_tenant_features(tenant_id)` → Pro's `FEATURE_MATRIX` has `voice_note: True`, combined with the global `FEATURES["voice_note_customer"]` flag (AND, not OR) — both true, so the gate passes (a Basic tenant would be blocked here and told "cuma bisa baca pesan teks & gambar"). `transcribe_audio_whatsapp(audio_media_id)` downloads and transcribes the note (uses `_active_whatsapp_access_token()` for the media download, i.e. THIS tenant's own token, not Kilas Works'); the transcript becomes `user_text` and `user_msg_is_voice_note = True`. From here the flow is identical to trace 2's text path: knowledge source `_build_tenant_context_block_safe(tenant_id)`, conversation-state key `_ck(tenant_id, from_number)`, `call_claude(..., tenant_id=tenant_id, is_voice_note=True)`, and outgoing send via that tenant's own active WhatsApp channel (never Kilas Works' global one).
