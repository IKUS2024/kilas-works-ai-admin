## Evidence and implementation

The previous player waited for the provider's complete MP3, duration validation, settlement, turn completion, a full download and `decodeAudioData`. The backend already used ElevenLabs HTTP streaming and a turn-local connection pool; neither was missing. Current primary references: [ElevenLabs HTTP stream](https://elevenlabs.io/docs/api-reference/text-to-speech/stream), [Chrome MSE audio/MP3 chunks](https://developer.chrome.com/blog/media-source-extensions-for-audio), [Chrome autoplay policy](https://developer.chrome.com/blog/autoplay/). The cloud Chromium capability probe returned `MediaSource.isTypeSupported('audio/mpeg') = true`. This does not prove iOS/Android device support.

The backend now publishes an initial small prefix of the SAME already funded/reserved whole-script TTS response, then bounded chunks. Its existing ownership/End fence remains before publication. The original 16KiB subsequent fence cadence is retained; a 4KiB initial network read avoids waiting for a 16KiB fill before initial delivery. No second synthesis, sentence splitting, model change, speculative translation, stale credit authorization, or quality/normalization option is introduced.

`GET .../audio/progress?offset=N` checks current authenticated owner, active session, exact owned turn/audio job and selected/actual pair on every read. It returns at most 64KiB at an immutable offset; repeated reads cannot advance a server cursor or cause provider work. No streaming HTTP generator holds a web worker. No progress URL is advertised until actual prefix bytes exist, avoiding a second polling loop during provider TTFB. One client read is in flight at a time; empty polls back off 40→80→160→250ms. Reads are bounded before assembling response bodies, regardless of a false Content-Length. Offset/size/status/digest/path changes fail closed.

Supported clients append chunks sequentially to one MSE MP3 decoder connected to the already unlocked AudioContext. Unsupported clients select the existing whole-file player before any speech is submitted; they do not dispatch an alternate request. Once progressive playback is attempted, a decoder/transport error is truthful and does not automatically replay the whole file or retry synthesis. The player waits for actual media end and full final validation, not a wall-time success. Mic/next capture stays locked while either producer or playback remains pending. Underflow can stall audio on a slow network; late bytes resume the same stream, and permanent stalls fail rather than silently dropping the tail.

The existing final MP3 duration check and settlement remain authoritative. Only after those finish does the relay return final size/SHA256. The client verifies its assembled bytes against that digest and the completed turn digest; only completed output gains replay. It caches these same bytes under the normal final URL, so replay does not refetch or regenerate. Prefix playback necessarily precedes validation of the entire future tail; malformed/truncated final output is an error and never becomes a successful completed artifact.

End discards pending bytes and stops media immediately. Background interruption preserves a bounded playhead offset, then normal authenticated reconnect reads the existing completed result and resumes its validated buffer near that position (conservative 100ms overlap to avoid clipping decoder boundaries). It does not repeat the whole heard prefix or re-send old speech. End clears offsets/cache; offsets are capped at 50 entries. A foreground recovery does not grant funding or replay a provider request.

Bounds: provider output and accumulated client bytes remain 20MiB maximum, relay responses 64KiB; existing temporary-entry count/expiry, two processing slots and client 24MiB/50-audio cache remain. The temporary progress buffer is discarded when final validated bytes replace it. Producer accumulation plus progress/final conversion has transient bounded copies; maximum-size production RSS/throughput is not claimed measured by small fixtures. SourceBuffer appends are sequential and acknowledged; no unbounded append queue. No new persistent storage or provider bandwidth request is added.
