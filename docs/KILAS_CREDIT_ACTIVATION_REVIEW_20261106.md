## Inactive safety fixes found in full diff review

- Customer receipt settlement is distinct from provider request accounting. A valid unreadable result remains a completed supplier request but releases customer credit. The proposed customer-success condition is validated readable=true plus a positive amount and supported currency. Refusal, invalid/oversized output and known rejection release customer holds; ambiguous transport stays reserved until evidence-based review. No automatic paid retry is added. This customer-facing success condition is explicit in all four consent languages and remains an unapproved production term.
- Receipt credit requests now reject inputs outside a single image of at most2048px per side/5MiB,64 category names of at most160characters each, and a12,000UTF8-byte aggregate text/schema/framing envelope. Nothing is silently cropped, resized or truncated by this hook. Existing active paid plans retain their original receipt input profile and CHAT accounting with no new wallet admission; a dedicated regression verifies this preservation. Other Finance flows and disabled-activation behavior are unchanged.
- The receipt profile's32k input value is a FORECAST, not an API-enforced input-token maximum. Exact GPT6Luna vision accounting was not established by the current official model sizing table; it lists other named models and detail-dependent behavior. An explicit matching input_accounting_verified contract marker is required in the tariff configuration, is NOT installed, and MUST NOT be set merely to pass configuration validation. The5-credit/32k economics are not certified. Before activation, establish the model-specific image-token ceiling or use a provider-supported preflight/hard bound; output is capped at2048 completion tokens. No supplier test was made.
- Quote retries are additionally bound to the original authenticated account and operation through a server-checked consent header. Account switching, operation changes, expiration or activation rollback cannot redirect an approved request into another account/legacy purchase path.
- Existing unlinked legacy Audio jobs retain duplicate retrieval across activation; no new admission or trial is created for the accepted old key. A SQLite/PostgreSQL regression verifies this.
- VO request fingerprints bind the resolved provider model. A voice/profile change from v2 to v4 requires a new approval; dispatch uses the admitted personal-voice mode instead of silently rereading a changed mode.
- Image generation pins the actual server default model in both profile and dispatch. Work image attempts keep a stable logical key when credit policy is on, preventing automatic retries from becoming new billable operations.
