## Evidence and diagnosis

The coordinating agent read a screenshot with the client message “The input connection fell too far behind. The session paused to avoid truncating speech. This speech will not be retried in another mode.” This identifies the client's `realtime_queue_full` guard; the screenshot alone cannot identify the underlying network, device or server delay. Read-only production logs show one `realtime_input_idle` at 2026-10-19 09:44:54 UTC (5,695 ms elapsed, fresh credit read 1,589 ms, connect 203 ms), among completed turns. There is no device trace linking that server event to the photographed client overflow, so the two are not asserted to be the same turn.

Confirmed reproducible defect: each queued HTTP request contained a frozen maximum one second of PCM and requests waited serially for their predecessor's acknowledgment. Any sustained HTTP round trip above one second therefore increased backlog even when every request succeeded. The original adapter reproduced `realtime_queue_full` after 16.4 seconds of capture at synthetic 1,500 ms HTTP RTT, with zero commits and one cancellation. Earlier 350 ms tests did not exercise this throughput ceiling. This defect is independent of selected language or direction.

## Focused correction

One serial writer now chooses each payload only after the preceding acknowledgment, combining **unsent** PCM already waiting in the same turn. The start response explicitly negotiates `pcm-coalesce-v1`: up to four seconds per HTTP payload. Healthy capture retains one-second batching; the first frame still primes input and release immediately drains the final partial tail. No intentional four-second waiting window is added. Legacy clients retain one-second admission. Unsupported/invalid negotiation fails closed.

The existing **eight-second total backlog**, 180-second audio cap, strict indexes/final count, timeout, one input lease, one final commit, cancellation settlement, quota and monetary accounting remain. This changes request granularity, not backlog/cost limits. The backend splits coalesced HTTP payloads into the same <=one-second supplier messages and preserves the existing 20-second provider commit boundaries. No parallel writers, retransmission, alternate ASR submission or duplicate supplier generation is introduced. Numeric accepted/sent/peak-backlog/last-chunk-gap diagnostics distinguish later failures without audio, transcripts, user IDs or keys.

Browser capabilities are selected before speech: AudioWorklet PCM when available, otherwise supported MediaRecorder batch. Explicit preselected batch mode survives technical renewal even when the account supports realtime. This is not fallback after an uncertain paid input. WebM/Opus, MP4 and Ogg/Opus probes cover the existing browser recorder path; a missing optional `isTypeSupported` probe uses the browser's native constructor default. Unsupported capture stops before speech/provider dispatch. No user-agent sniffing or permission bypass.

## Intermittent quiet output

Source inspection found no language-dependent volume setting, gain node or ducking control: both full/replay and progressive audio connected at unity. The media element is explicitly nonmuted at volume 1. No source boost, normalization, limiter, voice/model switch or modified cached bytes was justified by evidence.

On platforms exposing the optional `navigator.audioSession` API, Translator now declares capture as `play-and-record`, returns to `playback` only after microphone cleanup, and restores the previous type on End. A capture epoch prevents stale startup/capture callbacks from changing a newer turn's route. This addresses an unmanaged browser/OS focus transition; whether it caused the owner's intermittent quiet sound remains unproven without physical device output evidence. Unsupported/rejected optional APIs leave the existing path usable. User/OS volume is not altered.

Primary reference: [W3C Audio Session working draft](https://www.w3.org/TR/audio-session/) defines the capture/playback types and automatic audio-focus interaction. It remains a draft, not proof of a specific iPad implementation or speaker route.
