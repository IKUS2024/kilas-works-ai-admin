# Translator remembered speech-processing permission

Follow-up to `5ebc0c89d792b1c21f0ff20a827e457cc0a8e297`, completing the recurring-checkbox request described in [the previous UI checkpoint](QA_VOICE_SAMPLE_CONTROLS_20261017.md).

## Behavior and authorization

Classic Translator now presents an explicit first-use **Allow and start** action, with no checkbox. Before acceptance, the notice identifies ElevenLabs for speech transcription/translated speech and OpenAI for text translation, discloses that audio may be sent while speaking, and explains account-level memory and revocation. The authenticated user must affirm that they have the speakers' permission; neither ownership of saved voices, a past message, nor a login creates a grant. The policy remains accessible in the collapsed Speech processing permission setting, without requiring a link visit.

Successful admission stores user, processing scope, version and UTC acceptance timestamp in the new `kilas_translator_consents` table. There is no backfill. The current scope is `live-translator-elevenlabs-openai`, version `2026-10-17-v1`; recipient/scope or policy version changes require a new explicit affirmative action. Unchanged, unrevoked consent allows subsequent plain **Start**, including after a new authenticated login, without rewriting its acceptance timestamp. The database is the authority; cookies, local storage and browser flags cannot grant consent.

First-use acceptance is submitted only by the affirmative button's form submitter. Start validates the current scope/version and either a fresh explicit acceptance or an existing valid record before audio admission. It rechecks under the same owner lock and transaction as session creation. Invalid language, busy-session or other failed session creation does not leave a new grant behind. An old `consent=yes` checkbox POST alone cannot grant the new permission. Missing, obsolete, invalid and revoked records fail closed. A stale remembered page fetches the current disclosure after rejected admission and requires a new gesture; the microphone is not opened on that failure.

The accessible Speech processing permission setting offers **Revoke permission**. Its authenticated, CSRF-protected POST marks all versions of this owned scope revoked, ends owned classic Kilas Male/Female sessions, cancels their processing turns and clears local temporary output/relay caches. Existing cross-worker End watchers stop other worker relays. Audio upload/realtime input admission and classic Resume status enforce the current record. BroadcastChannel notifies other tabs to re-read their own server state and stop local media. Other users and native Gemini sessions/consent remain separate. Revocation cannot undo audio already sent or provider work already dispatched, as described by the existing privacy policy; no refund, zero-retention or instantaneous remote-device microphone claim is made.

## Persistence and scope

Migration `0104_kilas_translator_consent` creates only an initially empty table, keyed by user/scope/version, with acceptance and revocation timestamps. It uses the existing checksum-idempotent Audio release mechanism and SQLite migration list. No existing row, saved voice, audio artifact or transcript is migrated or deleted. Translation/capture/playback algorithms, provider/model dispatch, quotas and pricing remain unchanged. Finance, Group, Call, Voice Over and Creative Services implementation is preserved.
